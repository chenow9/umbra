# Umbra 映射模式与限速验证

测试日期：2026-08-29  
服务端：`192.168.10.112`  
目标节点：`192.168.10.111`  
访问测试端：`192.168.20.4`

## 1. 结论

映射模式均按当前设计生效：

- **公开模式：通过。** 公网入口持续监听，可直接访问目标服务。
- **暗端口（SPA）：通过，但授权粒度和会话语义需要注意。** 未敲门时访问超时；敲门后 60 秒内可访问；授权过期后新连接和已有连接都会失去通信。
- **访客模式：基础行为通过。** 不创建公网业务端口，管理端“探访”经访客路径成功往返 49 字节。本次未签发 24 小时访客票据，因此没有把长期票据复制到其他机器。

128 KB/s 限速也确实生效，但准确语义是：

- 限制整个映射的**入口方向**，不是每连接独立限速。
- 使用固定 1 秒字节窗口，按 1 KB = 1,024 字节计算。
- TCP 超限时关闭连接；UDP 超限时直接丢弃数据包。
- 它是流量管制（policing），不是平滑带宽整形（shaping）。

如果产品文案“限速”意味着连接应保持、流量稳定在配置值，那么当前实现不符合该用户预期；如果预期是超限即拒绝，则实现有效。

## 3. 模式验证结果

### 3.1 公开模式

从 `192.168.20.4` 直接访问服务端 30220：

- TCP 建连成功。
- 64 字节请求/回显成功。
- 首次回显 RTT 约 0.966 ms。

结论：公开模式会持续创建公网监听，可直接到达节点目标。

### 3.2 暗端口（SPA）

| 阶段 | 结果 |
|---|---|
| 敲门前 | 3.002 秒超时，无回显 |
| 管理端敲门后 | 立即成功，首次回显 RTT 约 1.125 ms |
| 60 秒授权过期后 | 再次 3.002 秒超时 |
| 已建立连接跨越 60 秒 | 前 11 次周期回显成功；授权到期后的下一次读写超时，连接未保持到 75 秒截止时间 |

管理界面的状态同步从“未敲门，外网不可见”变为“外网可连”，到期后自动恢复“未敲门，外网不可见”。

注意：当前 SPA grant 以 mapping ID 为粒度，是映射全局 60 秒放行，不绑定实际访问者源 IP。也就是说，一次敲门会在窗口内对所有可达该入口的来源生效。模式功能有效，但这不是“只允许敲门者”的细粒度授权。

当前 60 秒由控制端代码固定为 `60*time.Second`，UI、映射字段和环境变量均不能配置。服务端实际运行 nft 内核隐匿模式；授权到期后重新安装的规则按目标端口直接 DROP，没有“已建立连接继续放行”的 conntrack 例外。因此已有 TCP 连接不是收到 RST 立即退出，而是在下一次通信时无响应并最终超时。若服务端因权限问题退回用户态隐匿，已有 TCP 连接的表现可能不同。

### 3.3 访客模式

- 映射没有入口端口，服务端没有创建对应公网业务监听。
- 管理端显示“访客模式，入口无端口”。
- “探访”操作成功，入口与出口各计 49 字节。
- 目标节点回显正常。

这验证了控制端内部的访客映射路径和目标可达性。若需要完整验收访客端 CLI，还应另行签发临时票据，在第三台机器运行 `umbra-visit`，验证本地 L4 监听、票据撤销和过期行为。

## 4. TCP 限速验证

限速配置：128 KB/s。

### 低于限制

单连接每秒发送 64 KiB 请求，目标回显相同数据：

- 首包成功。
- 保持期 4/4 次回显成功。
- 连接保持正常，最终探测成功。
- 保持期双向统计为 512 KiB；入口方向约为其一半，低于 128 KiB/s 限制。

### 高于限制

单连接一次发送 256 KiB：

- 建连成功，但首次完整回显失败。
- 客户端在约 2 ms 内收到 TCP RST。

另一次快速流式发送同样很快出现发送和接收错误，连接未保持到截止时间。

### 映射全局共享

同一映射上并发运行快速流与低速周期请求时，快速流消耗映射字节窗口后，原本可正常工作的低速请求也收到 EOF。待窗口恢复并单独运行后，低速请求再次 100% 成功。

结论：TCP 限速是映射级共享预算；超限不会阻塞等待下一个窗口，而是通过写错误关闭整条 TCP 连接。

## 5. UDP 限速验证

报文大小 1,200 字节，单 UDP 流，固定速率开环发送。

| 输入档位 | 发送 | 回显 | 输入速率 | 回显速率 | 丢包率 | 结果 |
|---|---:|---:|---:|---:|---:|---|
| 50 包/秒 | 247 | 247 | 58.4 KiB/s | 58.4 KiB/s | 0% | 全部通过 |
| 200 包/秒 | 990 | 545 | 234.3 KiB/s | 129.0 KiB/s | 44.95% | 被限制在约 128 KiB/s |

高负载档位没有出现乱序、重复或损坏，未通过的数据包表现为直接丢弃。129.0 KiB/s 略高于 128 KiB/s 与固定窗口边界、定时精度和统计窗口未完全对齐有关。

结论：UDP 入口字节限制有效，行为符合固定窗口“超过预算即丢包”。

## 6. 可观测性问题

测试期间健康接口仍显示：

- `udpDropMaxConns = 0`
- `udpDropPerIP = 0`
- `udpDropRate = 0`

其中 `udpDropRate` 统计的是 UDP 新建流准入速率，不是 `rateKbps` 字节限速产生的丢包。因此 44.95% 的带宽限速丢包不会出现在现有健康指标中。TCP 因字节限速断开的次数也没有独立指标。

建议至少新增：

- `rateLimitDroppedBytes`
- `rateLimitDroppedPackets`
- `rateLimitClosedTCP`
- 每映射当前窗口已用字节和预算

## 7. 产品与实现建议

1. 将 UI 的“限速 KB/s”改成“入口限速（KiB/s）”，并明确“整个映射共享”。
2. 在帮助文案中明确当前行为：“TCP 超限断开，UDP 超限丢包”。
3. 如果产品希望保留长连接，应改成 token bucket/漏桶等待式整形，而不是返回写错误。
4. 评估分别配置入口和出口限速；当前只限制访问者/公网到节点方向，节点回包方向不受该值限制。
5. SPA 状态应提示“全局放行 60 秒”，或把 grant 绑定到来源 IP、身份和一次性 nonce。
6. 健康页和流量页应区分“新流准入限速”和“带宽限速”，避免两个“rate”概念混淆。
7. 将 SPA 授权时长做成映射级配置，并明确选择“到期中断全部流量”还是“仅禁止新连接、已有 TCP 连接继续”。

# Umbra L4 实验室容量诊断报告

- 日期：2026-08-28
- 用途：实验室容量**诊断**。不能当作吞吐上限或 10k 稳态能力签字。
- 四轮：
  - **r4（当前诊断）**：独立 Linux 发生器 `192.168.10.62`（32 核 / 31GiB / **1GbE**），同拓扑 Direct `G→111 echo` vs Umbra `G→112:公开口→隧道→111`；TCP stream 5 次重复；UDP open-loop 先找 Direct 丢包区间
  - **r3**：分窗/stream/open-loop，但 Direct 在 112、Umbra 发生器在 111（hairpin），拓扑不可比
  - **r2**：Mac Wi-Fi 发生器，过载 closed-loop
  - **r1**：发生器与入口同机；hold 失败被吞
- 原始文件：`docs/load-test-r4/`、`docs/load-test-r3/`、`docs/load-test-r2/`
- 标记：[Measured] / [Derived] / [Hypothesis] / [Caveat]

## 0. 给专家的结论

方法复核（相对 r3 跑数时的二进制）：

| 项目 | 结论 |
|---|---|
| hold 窗口独立统计 | 通过 |
| connect 与 firstEchoRTT 分离 | 通过 |
| TCP stream 独立读写 | 通过 |
| UDP 固定速率 open-loop | 基本通过；当时发生器会同步微突发（下轮前已加随机相位，未重测） |
| finalProbe | r3 串行；下轮前已改并发，且 **sem 之后重算 remain** |
| PID/cmdline 校验 | 通过 |
| 原始结果入库 | 通过 |
| r3 作为性能上限或代理开销 | **不通过**，定位为诊断 |

r3 按当前定位保留。不重跑 r3。

**可以确认：**

- Umbra 在第三台发生器场景下完成 10k TCP **首次** 32KiB 回显（r2，Mac→112:18000）。
- 在 r2 那种已经严重过载的 closed-loop 测试里，20 秒窗口出现大量超时；Umbra 多于 Direct。
- r2/r3 的 UDP 客户端成功率随并发流数下降，当时混有发生器过载、同步微突发和（r4）session 未隔离。**不能**据此写成 uplane 容量。
- r2 入口进程级 FD / `cpu_1s` / RSS 在校验过 pid 的那次采样里可信。

**暂时不能支持：**

- Umbra TCP 峰值是 35MiB/s（那是 Mac Wi-Fi closed-loop 的双向应用回显率，且把 setup 算进分母）。
- 1000 流是最佳吞吐点（分母含建连；且仍是 RR 不是 stream）。
- Umbra UDP 容量上限是 2.5MiB/s（closed-loop 超时会主动降载）。
- 10k Direct 与 Umbra 的差值就是代理开销（Direct 已过载，路径还少一跳）。

**r3 补充（LAN 虚机，iperf3 TCP P=1 为 27.9 Gbit/s）：**

- Direct TCP **stream** n=1：hold 窗 tx≈1.51GiB/s。Umbra stream n=1：tx≈181MiB/s；n=8：tx≈241MiB/s。这是独立读写的字节率，是性能**信号**，不是签字上限。
- Direct vs Umbra 拓扑仍不可比（112→111 vs 111→112→tunnel→111），**不能当代理开销**。
- UDP r3 Direct n=800 已丢 19%，Umbra 84% **不能全部归因于 uplane**（发生器当时同步微突发 + Direct 基线已过载）。

r3 **不需要为了“证明有效”而重跑**。

**r4（独立发生器，仍是诊断不是签字）：**

- 发生器 NIC 实测 **1000Mb/s full**。TCP stream n=1..32 各 5 次：Direct 与 Umbra 的 txRate **median 都在 110.7–114.1MiB/s**，txErr=rxErr=0，aliveAtDeadline=n。两边都被 G 的 1GbE 顶住，**不能**据此说 Umbra 达到或未达到隧道上限。
- UDP Direct open-loop n=20→800 pps=20：丢包均为 0（n=800 五次里一次 0.0002）。相位打散后 Direct 不再出现 r3 的 19% 基线过载。
- UDP Umbra n=800 五次 lossRate：**0.0005 / 0.0022 / 0.426 / 0.949 / 0.929**（median 0.426）。**不要**登记成「UDP 吞吐只有几 MiB/s」或「uplane 随机大量丢包」。
- 进程观测（cmdline 已校验）：gate cpu_1s 峰值 247、RSS 86MB、sock_fd 44；node cpu_1s 233、RSS 339MB、sock_fd 2002。无 pprof，不能拆 TLS/yamux/echo。

**r4 UDP 42%–95% 丢失的结论（已改分类）：**

1. **测试隔离 Bug（编排）**：五轮 n=800 连续执行，但上一轮 UDP session 要 60 秒才 idle 回收。800×8s 的 hold 结束后立即再开 800 条新源端口，`active` / node FD 累积到约 2000（映射 `MaxConns` 上限）。后续新 flow 被 Gate `!reserve()` **静默丢弃**（当时没有 drop reason / `udp_active` 指标），客户端表现为高丢包。这不是 uplane 转发性能 Bug。
2. **P1 工程缺陷**：UDP `MaxConns` 是 mapping **全局**配额。单个客户端用大量源端口即可占满，并在 idle 窗口内阻止其他客户端建 flow；且当时没有 admission-drop 指标。

已分别登记为两项，见 §7。本轮代码：每 IP flow 上限 + 新 flow 速率限制 + `udp_drop_maxconns` / `udp_active`（及 per-ip / rate）；r4 脚本每轮等 `udp_active=0`。

## 2. 工具（r3 已改）

`scripts/umbra-bench.go`：

- `setupElapsed` / `firstEchoBytes` / `holdElapsed` / `holdBytes` / `holdRate` / `totalElapsed` 分开。hold 窗从 setup 结束后才计字节。
- `connect` 与 `firstEchoRTT` 分开（Dial 结束才开始 echo 计时）。
- `-mode rr`：closed-loop 请求/响应。`interval=0` 只是不额外 sleep，**每连接仍只有一个请求在途**。
- `-mode stream`：TCP writer 持续写、reader 独立读，按字节计数。
- `-mode openloop`：UDP 固定 pps 发送，接收独立，超时不降发送速率。
- hold 内 op timeout = `min(timeout, remain)`，remain&lt;50ms 不再发新请求。hold 后短超时 `finalProbeOK`。`aliveAtDeadline` = hold worker 未见 echo 错误。
- `-json` 写出结果对象。

`scripts/umbra-obs.sh`：启动时写 `/proc/PID/cmdline`，可用第 4 参数做子串校验，防止再采错 pid。

**下轮前已改、尚未用新二进制重测：**

- UDP open-loop：每个 flow 随机初始相位；删除发送侧 `sent` map；接收侧 `seen` 改为 8192 序号滑动窗口（长 soak 用）。
- hold 窗内收到的包与 grace 迟到包分开（`holdRecv` / `graceRecv`）。
- `finalProbe` 按 `-par` 并发，**取得信号量后再计算 remain**，超时用该 remain，不会用排队前的旧截止。
- TCP stream：chunk 带序号+模式校验；**仅** `net.Error.Timeout()` 算 hold 正常截止，EOF/UnexpectedEOF/RST 在 drain 前一律 `rxErr`/`txErr`（回归：后端写 1 字节后 CloseWrite）；drain 并发且统一截止；每连接 tx 分位。

## 4. r2 应如何读（Mac Wi-Fi closed-loop）

发生器：MacBookPro18,3 **Wi-Fi**，到实验室要跨 `192.168.13.0`→`192.168.10.0`。iperf3 LAN 27.9G 与 r2 Direct 峰值 ~40MiB/s 对不上，所以 r2 不能代表隧道。

r2 仍有效的诊断：

- 10k TCP firstEchoOK=10000（Umbra 与 Direct）。
- interval=1s hold=20s：Umbra aliveAtEnd=6059 / failedDuringHold=3941 timeout；Direct 8807 / 1193。当时总速率把 setup+超时拖尾算进去，名义 20s 实际 56/65s。

- UDP-only RR：Umbra 1600 只有 19346 attempts，Direct 81600——超时把发送打下去了。

入口 obs（pid 校验过的 umbrad）：cpu_1s 峰值 228，sock_fd=10011，RSS 64MB→1.07GB；后来 RSS 73MB。节点 obs 那次采错 pid。

## 7. 缺陷登记

只登记下面两项。不要写成吞吐或 uplane 随机丢包。

### Bug：r4 UDP 测试轮次未隔离

- 等级：测试编排 Bug
- 现象：同一映射上连续五次 n=800 open-loop；session idle=60s，轮间隔远小于回收时间，`active`/node FD 叠到 ~2000。
- 机制：`serveUDP` 在 `!e.reserve()` 时 `continue`，无日志、无计数；新 flow 被静默丢弃，客户端 lossRate 从 ~0 跳到 42%–95%。
- 修复：`scripts/r4-run.sh` **fail-closed**：未观测到 `udpActive=0` 则中止，不带着残留 session 开下一轮；n=800 前确认 gate 实际 per-IP/rate/map 限额 ≥800 或为 0。
- 验收：五次独立 n=800 每轮都从 `udp_active=0` 开始；等不到 0 则该轮不跑。
- 状态：r4 原归因可接受。不重跑旧 r4；隔离后的容量测试走 r4b。

### P1：UDP 公网映射抗配额耗尽

- 等级：P1 可用性 / DoS（**尚未签字关闭**）
- 现象：`MaxConns` 是 mapping 全局计数。一个客户端用大量源端口即可占满配额，idle 窗口内其他客户端无法建 flow；且当时没有 admission-drop 指标。
- 已通过：idle 回收 + TypeClose、指标、基础 IPv4 per-IP/rate 隔离。
- 已闭环的阻断项：MaxConns 拒绝不增长 `udpIP`；drop 日志 mapping+reason 1/s；`wait_udp_idle` fail-closed；IPv6 /64 与 mapping 级 token bucket。
- 待签字前补丁（本轮）：
  - `releaseUDP` 先按 `last` 经过时间 refill token，再更新时间戳；长存活 flow 回收后立即 admission 不得误伤
  - TTL/LRU 改为最多每秒一次摊销扫描；拒绝路径不扫表；仅成功插入且达硬上限时 LRU
  - Direct climb：跑前删目标 JSON；bench 非零或 JSON 缺失则跳过该 n，不读残留、不更新 last_ok
- 失败 admission 仍不得创建新状态；immediate churn 仍不得重置 per-IP 速率。
- 容量测试若要从单 IP 打 n=800 转发，把 `UMBRA_UDP_MAX_FLOWS_PER_IP` / `UMBRA_UDP_NEW_FLOWS_PER_SEC` / `UMBRA_UDP_NEW_FLOWS_PER_MAP` 调到 ≥800 或 0。
